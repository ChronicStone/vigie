---
title: Status page
description: defineStatusPage chooses what the public /status page shows, from your monitors and alerts.
---

```ts [definitions/status.ts]
import { defineStatusPage } from '@vigiejs/sdk'
import { noPayments } from './alerts/acme.ts'
import { api, shop } from './monitors/acme.ts'

export const status = defineStatusPage({
  title: 'Acme status',
  description: 'The Acme shop, its API and payments.',
  public: true,
  components: [
    { name: 'Shop', from: shop },
    { name: 'API', from: api },
    { name: 'Payments', from: noPayments, group: 'Integrations' },
  ],
  days: 90,
})
```

A component is a monitor or an alert, so anything an alert watches can be on the page: an error rate, failed tasks, a queue. Only what is listed shows, in this order, under the names visitors read. Outages of anything else stay off the page.

| Field | What it does |
|---|---|
| `components` | `{ name, from, group? }`. `from` is a monitor or alert from your definitions, or `'monitor:<id>'` / `'alert:<id>'` for one made in the app. |
| `public` | Anyone with the link can open it. Leave it out to decide in the app. |
| `days` | 30, 60 or 90 days of history. |
| `show` | Turn sections off: `active` (open incidents and their updates), `history` (one bar per day, per component), `uptime` (the share of time each component was up), `past` (resolved incidents). All are on by default. |
| `title`, `description` | The heading and one line under it. |

When this file exists, it takes over: the **Status page** screen shows it read-only. Define only one status page: if there are several, the last one loaded is used. Incidents and their updates stay runtime data, written on that screen or by an agent. See [Status page](/docs/features/status-page).
