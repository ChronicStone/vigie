A process is a flow that crosses several background tasks, such as an order going from payment to parcel. Vigie groups task attempts by the object they work on and shows where each one is.

```ts [definitions/processes/acme.ts]
import { defineProcess, step } from '@vigiejs/sdk'

export const fulfilment = defineProcess({
  id: 'order-fulfilment',
  title: 'Order fulfilment',
  subject: 'order',
  keyPrefix: 'order:',
  description: 'From a Paynest payment to a parcel on its way.',
  sla: '4h',
  steps: [
    step.task('paynest.payment.ingest', { label: 'Payment confirmed by Paynest', expectWithin: '30m' }),
    step.parallel([
      step.task('receipts.email', { label: 'Customer emailed', expectWithin: '1h', optional: true }),
      step.task('parcelo.ship', { label: 'Shipment created at Parcelo', expectWithin: '15m', provider: 'parcelo' }),
    ]),
  ],
})
```

## How an attempt joins an instance

Each task attempt says which object it works on, with a `task.key` such as `order:o_81`. Attempts with the same key are one instance. Only keys starting with `keyPrefix` belong to the process. Put the key on the attempt's wide event:

```ts
await task({ kind: 'parcelo.ship', id: job.id }, async ({ log }) => {
  log.set({ task: { key: `order:${order.id}` } })
  await parcelo.ship(order)
})
```

If the event has `task.subject.id` (and `task.subject.type`), that id is the instance instead of `task.key`. Without any key, an attempt belongs to no process.

_The `order-fulfilment` process above, on demo data: the funnel, then each order that is stuck or failed and why._


| Field | What it does |
|---|---|
| `subject` | What one instance follows, in your words. |
| `keyPrefix` | Only task keys that start with this belong here. |
| `steps` | `step.task(kind, { label, expectWithin?, optional?, provider? })`, and `step.parallel([...])` for steps that run side by side. `kind` is a task kind. |
| `expectWithin` | `30m`, `1h`, `24h`: units are `s`, `m`, `h`, `d`. A step that has been waiting to retry longer than this, or a required step that has not started this long after the instance's last attempt, makes the instance **stuck**. |
| `optional` | The instance can finish without this step. |
| `sla` | The time the whole flow should take. Shown on the process. |
| `standing` | For flows on a clock, with runs instead of instances: it has no instance list. |
| `aliases` | When some tasks name the object by another id, such as the provider's, read the mapping from your app's database (`VIGIE_APP_DATABASE_URL`): `{ subjectType, table, aliasColumn, subjectColumn }`. Without that database, the aliases stay separate instances. |

An instance is **done** when every required step has succeeded, **failed** when a step failed and will not retry, **stuck** when it waits too long, and **running** otherwise.

The **Processes** screen shows the funnel, the stuck instances with the reason from their last attempt, and each instance's timeline. Agents read it with `list_processes`, `get_process`, `list_stuck_instances` and `get_process_instance`.
