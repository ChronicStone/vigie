---
title: MCP
description: Agents read the same screens you do through the Model Context Protocol, and act on them with a write token.
---

`<VIGIE_URL>/mcp` speaks MCP over HTTP (JSON responses). On your machine it needs no token. On a server, create an **MCP** token on **Settings, Tokens**, with a scope:

- A **read** token gets the read tools: logs, traces, tasks, issues, processes, metrics, the status page.
- A **write** token also gets the tools that change something: resolve or mute an issue, pause or create an alert, declare an incident or a deployment, create a monitor or dashboard.

A signed-in person's own role decides the same way: viewers get the read tools only.

Agents cannot requeue, cancel or run tasks. Those actions call your app as a signed-in person, so they are not offered over MCP at all. See [Tasks](/docs/features/tasks#acting-on-tasks).

Payloads never leave through MCP: tools return fields and summaries, with secrets already masked at ingest.

## Connect an agent

```json [.mcp.json]
{
  "mcpServers": {
    "vigie": {
      "type": "http",
      "url": "https://vigie.example.com/mcp",
      "headers": { "authorization": "Bearer vm_…" }
    }
  }
}
```

Start with `get_context_pack`: a short brief of the running system, with traffic, errors, open issues, firing alerts, failing tasks and the state of each process, so the agent knows your app's words before it asks. `whoami` says who the agent is and which role it has.

## What it can do

More than a hundred tools, grouped like the screens. These are the ones to know; the agent lists the rest itself:

| Area | Tools |
|---|---|
| Logs and traces | `search_logs`, `list_logs`, `get_event`, `get_trace`, `get_trace_logs`, `list_traces`, `get_request` |
| Tasks | `list_tasks`, `get_task`, `get_task_timeline`, `list_task_failures`, `get_task_health`, `list_task_kinds`, `list_schedules`, `list_workers` |
| Issues | `list_issues`, `get_issue`, `resolve_issue`, `mute_issues`, `create_linear_issue` |
| Processes | `list_processes`, `get_process`, `list_stuck_instances`, `get_process_instance` |
| Alerts | `list_alerts`, `get_alert`, `create_alert` (starts paused), `update_alert`, `preview_alert`, `pause_alert`, `resume_alert`, `export_alert_as_code` |
| Status page | `get_status_page`, `declare_incident`, `post_status_update` |
| Releases | `declare_deployment`, `get_release_verdict` |
| Data | `run_query` (a read-only `SELECT` on telemetry), `list_tables`, `read_table`, and `run_readonly_sql` for your app's database when it is connected |

Every [page](/docs/definitions/pages) and every [`defineTool`](/docs/definitions/tools) becomes a tool too.
