---
title: Releases
description: Mark each deploy, and Vigie tells you whether it made things worse.
---

Declare a release from CI, after the deploy:

```bash
bunx @vigiejs/cli deploy --url https://vigie.example.com --token vd_… --service acme-api --version $GIT_SHA
```

Create a **deploy** token on **Settings, Tokens**. `--env` is the environment Vigie files it under, `PRD` by default (`STG` or `DEV` on a server that keeps them). `--url` and `--token` can also come from `VIGIE_URL` and `VIGIE_DEPLOY_TOKEN`. It prints `Declared acme-api <version>`, and fails with Vigie's answer if the token or address is wrong.

Declaring is optional. Vigie notices every new `service.version` on incoming data on its own and marks it as detected: declaring adds who and when. Set the version on your telemetry (`APP_VERSION`, or `service.version`) for either to work.

The **Releases** screen gives each version a verdict, from the hour after it first appeared against the hour before: error rate and p95 latency, plus issues that came back with it. A release is a **regression**, **changed** or **clean**, or **unknown** when fewer than 20 requests came in the hour before, which is too few to judge.

Agents read it with `get_release_verdict`, and can declare one with `declare_deployment`.

With `VIGIE_SOURCE_REPO` (`acme/shop`) and `VIGIE_GITHUB_TOKEN` set, Vigie shows the source lines behind an error's stack frames, read from GitHub at the release's commit. This only works when the version is a full commit SHA (7 to 40 hex characters): a tag such as `1.4.2` shows nothing, because it could point at other lines. If your repository keeps the app in a subfolder, set `VIGIE_SOURCE_PREFIX` to that path, with a trailing slash (`apps/api/`).
